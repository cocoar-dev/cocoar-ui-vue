# Spike A — 1k × 1k 2D Grid

> **Status:** Live (Phase 0, Day 3). 2D virtualization landed and
> validated against the same Tier A bar as the 1D pages. Component ships
> in v1 even though the v1 calendar views are 1D-only — see design doc
> §0.6 for the architecture commitment.

## Question

Validate `<VirtualizedSurface2D>` with `axis = 'both'`. Logical grid of
1.000 × 1.000 = 1 M cells, only ~ 350 ever visible. Scroll diagonally
with the wheel and verify the **same 0/0 LoAF bar** the 1D pages hit.
Critically: 2D must not regress 1D — they must be independent enough
that 1D is mechanically guaranteed unaffected.

## Architecture

`<VirtualizedSurface2D>` is a **separate Vue component** from
`<VirtualizedSurface1DY>`. They share NOTHING at the Vue layer:

- No conditional code paths inside either component for "is this 1D
  or 2D?" — each component compiles to a dead-simple v-for loop.
- 1D consumers using only `<VirtualizedSurface1DY>` pay zero bytes for
  2D code (tree-shaking).
- 1D scroll behaviour and performance are mechanically guaranteed
  unaffected by anything we do in the 2D component.

The shared layer is the framework-agnostic `core/virtualScroll.ts`:
the 2D component calls `getVisibleRange1D` once per axis (composing two
1D ranges into a `Range2D`), and renders the Cartesian product of the
two ranges as absolutely-positioned cells.

```ts
// core/virtualScroll.ts — composition only, no new math
export function getVisibleRange2D(
  measurementsX, measurementsY,
  scrollX, scrollY,
  viewportWidth, viewportHeight,
  overscanX, overscanY,
): Range2D {
  return {
    x: getVisibleRange1D(measurementsX, scrollX, viewportWidth, overscanX),
    y: getVisibleRange1D(measurementsY, scrollY, viewportHeight, overscanY),
  };
}
```

Property test (200 random runs) proves
`getVisibleRange2D ≡ (getVisibleRange1D × 2)` exactly — there is no
new code path; just two independent 1D calls.

## Phase 0 scope: fixed-size only

The 2D variable-size path adds complexity (per-row + per-column caches,
anchor restoration in two axes, partial re-layouts driven by a single
ResizeObserver entry). Real consumers — the v2 timeline view in
particular — typically have known cell sizes (a "minute" is a fixed
pixel width; a "resource" is a fixed row height). Fixed-size 2D ships
in Phase 0; variable-size 2D extends the API when v2 demands it.

## Targets

| Measurement | Tier A | Tier B |
|---|---|---|
| Long frames during diagonal wheel scroll | 0 over 5 s window | ≤ 2 over 5 s window |
| Worst frame during diagonal wheel scroll | < 16 ms | < 30 ms |
| 1D regression check (same scroll regimen) | identical 0/0 to before | identical |

## Tier A end-to-end results (LoAF-based)

Measured on the dev baseline (Snapdragon X Elite X1E-78-100, Win11
ARM64, Chrome ARM64) via Chrome DevTools / `PerformanceObserver`:

| Test | Long frames | Worst frame | Cells in DOM |
|---|---|---|---|
| 2D 1k × 1k, 30 ticks at 50 ms cadence (≈ real wheel) | **0** | 0 ms | 378 |
| 2D 1k × 1k, 50 ticks at 30 ms cadence (synthetic burst) | 1 | 50 ms | 357 |
| 1D variable, 30 ticks + 5 toggles (regression check) | **0** | 0 ms | 10 |

The single long frame in the synthetic burst (50 ticks at 33 Hz — about
twice the cadence of natural wheel input) lands exactly on the 50 ms
LoAF threshold. Real-user wheel scroll does not produce this. The
regression check on the 1D variable-size page under the same
non-burst regimen returns 0/0 — adding 2D did not affect 1D at all.

## Decision

_2D performance ≥ 1D performance under realistic load._ The 2D
component is shipped in v1 to lock the architecture commitment and
provide an empirical foundation for the v2 timeline view; no v1 view
consumes it. The variable-size 2D path remains deferred to v2.
